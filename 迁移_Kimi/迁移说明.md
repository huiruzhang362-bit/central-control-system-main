## 0. 结论摘要

这个项目迁移**极其轻**，因为它是"零构建 + 依赖已本地化"的形态：

| 迁移面 | 实际情况 | 迁移动作 |
|---|---|---|
| 文件 | 核心 2.9 MB / 24 个文件 | 整目录拷过去即可 |
| 依赖 | **无** package.json、无 node_modules | 不需要 `npm install`，无需联网 |
| 配置 | 无 `.env`、无构建配置、无 CI | 无可迁配置 |
| 上下文 | `.workbuddy/memory/`（216 KB）+ `项目档案.md`（46 KB） | **必须转格式**，Kimi 没有 memory 机制 |
| 设计规范 skill | 用户级目录 + 2 处软链 | 修 frontmatter 后软链/打包 |

真正的风险不在"文件能不能拷过去"，而在**上下文会不会丢**：WorkBuddy 靠 `.workbuddy/memory/*.md` 自动注入记忆，Kimi 靠项目根的 `AGENTS.md`。这一步不做，新环境里的 AI 就是一个"读得懂代码但不知道你为什么这么改"的陌生人。

## 3. 迁移步骤

### Step 0 · 先让 Kimi 能说话（**当前卡在这**）

```bash
kimi login          # 设备码流程：给你 URL + 码，浏览器里确认
```

当前 `~/.kimi-code/oauth/kimi-code` 是 **0 字节**，`kimi -p` 直接报 `auth.login_required`。这步必须你本人在浏览器完成，我没法代办。
登录后所有动态验收项才能跑（校验脚本第 7、8 段）。

### Step 1 · 迁文件（同机 = 就地打开，不复制）

Kimi Code CLI 是"按工作目录工作"的，**同机迁移根本不用复制**：

```bash
cd /Users/roboticplus/Downloads/central-control-system-main
kimi                # 直接在这个目录开会话，文件、依赖、软链全都在位
```

**换机 / 换路径**才需要搬，用 `rsync` 保留结构与软链：

```bash
rsync -av --exclude '_p*.html' --exclude '.DS_Store' --exclude '.workbuddy' \
      /Users/roboticplus/Downloads/central-control-system-main/  <目标目录>/
```

> 用 `cp` 的话必须 `cp -a`（保留软链），否则 `型钢切优化/` 里的 `../antd.min.js` 软链会变成断链或实体副本。

### Step 2 · 依赖：不安装，只验证

没有 `npm install` 这一步。验证方式就两条：

```bash
ls react.min.js react-dom.min.js dayjs.min.js antd.min.js antd.min.css   # 5 个都在
open 中控系统.html                                                       # 双击能出界面
```

关键约束：`<script>` 引入顺序不能动 —— `react → react-dom → dayjs → antd → 加工任务_假数据.js → 排产_输入数据.js → 排产_算法.js → data.js → 主脚本`，错一个就白屏。

### Step 3 · 迁上下文（**最容易丢的一环**）

两边的机制根本不同，不能直接拷文件：

| 维度 | WorkBuddy | Kimi |
|---|---|---|
| 记忆载体 | `.workbuddy/memory/MEMORY.md` + 每日日志，自动注入 | **`AGENTS.md`**（无 memory 机制） |
| 项目级位置 | `.workbuddy/`（工具私有） | 项目根 `AGENTS.md` 或 `.kimi-code/AGENTS.md` |
| 用户级位置 | `~/.workbuddy/...` | `~/.kimi-code/AGENTS.md` 或 `~/.agents/AGENTS.md` |
| 历史会话 | 会话 JSONL | `~/.kimi-code/sessions/<workDirKey>/`，**只能导出不能导入** |

本次已把记忆里"对写代码有用"的部分提炼成项目根 `AGENTS.md`（116 行），结构是：

```
0 三十秒速览 → 1 五条铁律 → 2 技术栈 → 3 文件地图 → 4 设计规范（强约束）
→ 5 怎么跑/怎么验 → 6 提示策略 → 7 当前状态 → 8 不要做的事
```

**刻意没写进去的**：每日日志里的过程性内容（试了什么、怎么失败的）。这类信息价值随时间衰减，留在 `.workbuddy/memory/` 归档即可；`AGENTS.md` 只放**下次开工必须立刻知道**的东西（否则每轮对话都在烧 token 读历史）。

三条附加建议：
1. **`AGENTS.md` 要短**。它是常驻上下文，超过 200 行就该把细节挪进 `项目档案.md` 再引用。
2. **别用 `~/.kimi-code/SYSTEM.md`**。它会**整体替换**主 agent 的系统提示词（工具集、subagents 全变），改错能把 CLI 弄成残废。项目上下文用 `AGENTS.md` 就够。
3. 想让 WorkBuddy 侧的历史可追溯，用 Kimi 的 `kimi export` 或 TUI 内 `/export-md` 导出存档 —— 但那是**归档**，不是"迁过去还能接着聊"。跨目录复用旧会话官方文档没保证。

> **关于"Kimi 那边已有这个项目的上下文工作进程"**：实测查过了，`~/.kimi-code/sessions/wd_central-control-system-main_ca9715dc2a95/` 下只有一个会话（2026-10-22 14:19，`wire.jsonl` 18 KB），内容是当时做的一次 skill 加载探测（"列出你能加载哪些 skill"）。**没有任何项目业务上下文积累**。所以不要指望它能接上进度 —— 它的价值仅仅是"工作目录已登记过"，真正的上下文还是得靠 `AGENTS.md` 重建。

## 4. 设计规范 skill：组织、迁移、生效

### 4.1 组织原则：唯一真实来源 + 软链分发

```
~/.workbuddy/skills/dajie-orange-design-spec/     ← 唯一真实来源（源）
├── SKILL.md                    ← frontmatter + 使用流程 + 验收清单
├── references/
│   ├── components.md           ← 按钮/表格/分页/弹窗/导航…逐组件规范
│   ├── patterns.md             ← 页面级交互模式
│   └── 需求描述契约.md          ← 「基准 + 差异」的描述方法
├── assets/
│   ├── design-tokens.css       ← CSS 变量（--ctl-* / --cell-* / --fs-*）
│   ├── antd-config.js          ← ConfigProvider token
│   ├── patterns.css
│   ├── showcase.html
│   └── studio-drawer.html
└── tools/
    ├── build-spec.py           ← 合成单文件预览
    ├── variants/               ← 布局变体
    └── 设计规范总览.html        ← 唯一预览入口（预生成，不依赖 JS）
```

**铁律：项目里绝不放实体副本。** 一旦有第二份实体，"改规范"就会变成"改两份，然后两边不一致"，这种事发生过一次就够了。项目内如需引用，一律软链。

### 4.2 Kimi 的扫描路径与优先级

Kimi 认的是同一套 SKILL.md 标准，扫描顺序（越具体优先级越高）：

| 作用域 | 路径 | 本项目用哪个 |
|---|---|---|
| 项目级 | `.kimi-code/skills/` ｜ `.agents/skills/` | ✅ `.kimi-code/skills/`（双保险） |
| 用户级（Kimi 专属） | `$KIMI_CODE_HOME/skills/`（默认 `~/.kimi-code/skills/`） | 未用 |
| **用户级（跨工具通用）** | **`~/.agents/skills/`** | ✅ **主力，一定生效** |
| Extra | `config.toml` 的 `extra_skill_dirs = [...]` | 未用（备选） |
| 内置 | 随 CLI 分发 | — |

> 项目根的判定规则是"**从工作目录向上最近的含 `.git` 的目录**"。本项目**没有 `.git`** —— 所以项目级 skill 与 `.kimi-code/AGENTS.md` 未必被识别。这就是为什么主力走用户级 `~/.agents/skills/`（跟项目根无关，一定生效），项目级只作双保险。

### 4.3 三种落地场景

**场景 A · 同机（你现在的情况）—— 软链，零维护**

```bash
# 已在位，无需重做；改规范只改源目录，两边自动同步
ls -l ~/.agents/skills/dajie-orange-design-spec
# → /Users/roboticplus/.agents/skills/dajie-orange-design-spec -> /Users/roboticplus/.workbuddy/skills/dajie-orange-design-spec
```

**场景 B · 换机 / 给同事 —— 实体拷贝一份到用户级**

```bash
mkdir -p ~/.agents/skills
cp -R /Users/roboticplus/.workbuddy/skills/dajie-orange-design-spec ~/.agents/skills/
# 此时 .workbuddy 那份不存在，~/.agents/skills/ 这份升格为唯一真实来源
```

**场景 C · Kimi 网页版 / 桌面版 —— 账号级技能，走上传**

网页版读不到本机目录，只能上传。把 skill 打成 zip，在 Skills 面板用 Document to skills 上传（或给 GitHub 仓库 URL 安装）：

```bash
cd ~/.workbuddy/skills && zip -r ~/Desktop/dajie-orange-design-spec.zip dajie-orange-design-spec \
  -x '*.DS_Store'
```

> 网页版是**另存一份到云端账号**，之后改本机不会再同步。要么认这个分叉，要么改完重新上传。

### 4.4 怎么确认它真的生效

Kimi 会话里：

1. 输入 `/skill:` 看有没有 `dajie-orange-design-spec` 出现在候选里
2. 或直接问一句探针题：**「主色是多少、弹窗底部最多几个按钮、表格怎么对齐」**
   - 答 `#EE6402`、2 个、规范里的对齐规则 → 生效
   - 含糊其辞或答 antd 默认蓝 → 没加载

改完 SKILL.md **必须重开会话**，运行中的会话不会热加载。

## 5. 注意事项（坑清单）

| # | 坑 | 后果 | 规避 |
|---|---|---|---|
| 1 | `SKILL.md` 的 frontmatter 不是标准 `---`（如 `\---`、BOM、前导空行） | Kimi 静默不加载，**无任何报错**，最难查 | 校验脚本第 5 段；首行必须字面 `---` |
| 2 | 目录型 `SKILL.md` 缺 `name` 或 `description` | 该 skill 直接解析失败 | 两个字段必填，缺一不可 |
| 3 | 无 `.git` 导致项目根识别不到 | 项目级 skill / `.kimi-code/AGENTS.md` 未必生效 | 主力走 `~/.agents/skills/`；真要项目级就 `git init`（**先与用户确认**，别覆盖既有 GitHub Pages 链路） |
| 4 | 用 `cp` 而非 `cp -a` 搬目录 | `型钢切优化/` 的相对软链变断链 | `rsync -a` 或 `cp -a` |
| 5 | 把 `.workbuddy/memory/` 当上下文搬过去 | Kimi 不读，等于没迁 | 转成 `AGENTS.md` |
| 6 | 以为旧会话能导入 | Kimi **无 import**，会话按 workDirKey 分组 | 会话只作归档（`kimi export`），上下文靠 `AGENTS.md` |
| 7 | 改了根 `中控系统.html` 忘了同步交付包 | 发出去的演示包是旧版（**已经踩过一次**） | 校验脚本第 2 段强制查 md5 |
| 8 | `agent-browser` 未装就做前端验收 | 只能靠猜，视觉问题反复漏修 | 新机重装；验收必须在真实视口 + 真鼠标事件 |

