════════════════════════════════════════
一、项目是什么
════════════════════════════════════════

型材（角钢/型钢）立库与切割产线的工业中控系统 UI 原型。业务链路：型材按「船号 + 分段号 + 程序号」组织成切割包 → 从立库出库 → 经喷码、去底漆、切割、分拣五道工序 → 成为零件。

它的用途不是上线生产，而是三件事：
1. 与 Figma 设计稿（「数据报表_切割」「00-界面框架」）逐像素对齐，供设计师与业务方评审；
2. 客户/同事演示，不需要安装任何环境，双击 HTML 就能跑完整业务闭环；
3. 验证排产、实时推送、状态机、拖拽排序这些交互逻辑是否合理。

因此有三条定性必须先记住：
- 全部数据是演示用假数据。无后端、无真实接口、无鉴权、无权限校验。
- 目标环境是 1920×1080 桌面浏览器 / 工业大屏，缩放 100%。明确不做移动端适配。
- 「双击就能跑」是核心交付价值。任何让它需要构建、需要联网、需要启动服务才能运行的改动，都等于毁掉这个项目。


════════════════════════════════════════
二、五条铁律（违反会直接破坏演示可用性）
════════════════════════════════════════

1. 不引入构建流程。禁止 JSX / Babel / npm / Vite / Webpack。所有组件用 React.createElement 手写。不要提议「拆文件」「组件化重构」「加 TypeScript」——这些对原型是负收益。

2. 不改 <script> 引入顺序。顺序固定为：
   react → react-dom → dayjs → antd → 加工任务_假数据.js → 排产_输入数据.js → 排产_算法.js → data.js → 主脚本
   顺序错会因全局变量未定义而白屏。

3. 不在 data.js 与主脚本里重复声明同名全局变量。两者同处全局作用域，重复声明会 SyntaxError。

4. 不擅自升级 React / antd 版本号。本地打包的 UMD 文件（react.min.js / react-dom.min.js / antd.min.js / dayjs.min.js / antd.min.css）是离线演示的基础，全部就在项目根目录。

5. 不删除、不重命名中文文件名。多个 HTML 之间通过百分号编码的中文路径互相引用（含 iframe）。写路径时必须正确编码。

5.8 弹窗（最高频出错点，逐条对照）
- 相对整个页面居中，右上角必须有关闭按钮。
- 内容区与页头间距 20px。标题 16px Medium、85% 黑，且不重复正文内容。
- 底部操作区只有一个形态：右对齐、恰好两个按钮、「取消（描边）在左 + 主操作（橙实底）在右」、gap 8px、不加分隔线、内边距 12px 24px 20px。
- 严禁：三个及以上按钮；把取消做成右下角文字链接；只有确定没有取消（纯提示型弹窗除外）。
- 如果需求确实有三个动作，把次操作移到内容区右上角或步骤行右侧，footer 保持两个。
- 主操作文案用动词（保存并提交 / 确认删除 / 创建），不要用「确定」这种无信息量的词。
- 危险确认弹窗：警示图标（主橙）+ 标题 + 说明 + 取消/主操作。
- antd 写法：用默认 footer 的 okText / cancelText，不要传自定义 footer（只读详情弹窗传 footer: null）。
- 抽屉宽度给整数（如 560）。

5.16 样式改动的三级覆盖（判断顺序很重要）
① 能加修饰类（大按钮 / 小按钮 / 危险按钮）解决的，不要开作用域；
② 能给模块根容器加作用域属性解决的，不要动全局 :root；
③ 只有全站基准真的不合适，才改 :root 的 token。
层级错了会把一个局部问题扩散到全站，这是返工的第二大来源。

5.17 设计规范铁律
1. 禁止自创样式与展现形式。有规范按规范，没有就先问我。
2. 全站不用纯黑文字；主色只用 #EE6402 家族；不允许出现 antd 默认蓝。
3. 禁用态元素不要 hover / click 高亮。
4. 表单内一行内容不换行。
5. 改样式时只动目标范围，不牵连其他页面的布局与间距。
6. 删除等危险操作的弹窗全站统一形态。
7. 布局优先复用已登记的结构，不凭描述现编。
8. 组件 CSS 不写死尺寸与字号，用 token。（本项目历史代码里有部分写死值，新代码不要再犯。）
9. 改样式先定位覆盖层级。
10. 「只改样式」的任务禁止越界：不动业务逻辑、数据结构、路由。


════════════════════════════════════════
六、提示（toast / 弹窗）策略
════════════════════════════════════════

全站轻提示收敛在 useMsg() 策略层（中控系统.html 第 923 行附近），不要在调用点各弹各的。四级判定：

L0 error    操作无法继续、且用户需要知道原因才能自助恢复（数据冲突、前置状态不满足、推送失败）→ 必留
L1 warning  操作被驳回，或存在真实业务风险（未勾选、状态不允许、已出库无法撤回）→ 必留
L2 info     不改变状态，但它是某个动作的唯一反馈（暂未实现、已在运行中）→ 必留但缩短时长
L3 success  纯成功回执 → 默认静默，只有导出、下发、删除这类有留存价值的才保留

另外三条已定策略：
- 同文案 2.5 秒内去重，同屏最多 2 条，单条 1.6 秒。
- 低等级删除不做二次确认：工单、上传文件、用户/角色/班次/日志、撤回型材与撤回组，点击即执行 + toast 回执。仅「下发」这类不可逆业务动作保留确认弹窗。
- 新增提示时先判断属于哪一级，不要默认弹 success。
