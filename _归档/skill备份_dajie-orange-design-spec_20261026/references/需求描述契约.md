# 需求描述契约（怎么跟 AI 说要什么，才能又规范又不重复）

> 适用场景：多个项目共用同一套设计规范，但字段数量、按钮数量、业务语义各不相同。
> 目标：**只描述差异，不重复描述母版；该锁死的自动锁死，该变的说清楚变在哪。**

---

## 0. 一条判据：什么锁死，什么自由

拿不准某样东西该不该变时，用这一条判断：

> **让人「看起来同不同」的，锁死；让人「读到什么内容」的，自由。**

| 归谁 | 具体是哪些 | 举例 |
|---|---|---|
| 视觉参数 → **锁死** | 色值、圆角、字号阶梯、字重、控件高度、间距网格、阴影、层级、对齐方式 | 按钮就是 4px 圆角 32px 高，不能因为"这个项目想圆一点"就变 |
| 业务实体 → **自由** | 字段名、列名、按钮文案、按钮个数、数据、图标选择、模块组合顺序 | 这个项目要 5 个字段、3 个按钮，完全可以 |

灰色地带（规范没写过的新东西）：**先问，不要猜**（铁律 1）。
规范写过但这次业务确实要不同：**可以破，但必须写进「允许偏差」并给理由**，否则半年后没人解释得清为什么这里跟别处不一样。

## 1. 三层分权

| 层 | 名字 | 内容 | 需求里要不要写 |
|---|---|---|---|
| **L0** | 锁死层 | 品牌色 `#EE6402`、四级文字色阶、圆角（卡片 12 / 按钮 4 / 输入 2）、字号阶梯（16/14/12）、间距 8 网格、阴影值、按钮三档高度（40/32/24）、控件高 32、表格密度、弹窗 12px 圆角、footer 形态 | **不用写**。规范文件已定，写了也是冗余 |
| **L1** | 槽位层 | 按钮（按角色，数量可变）、字段（按语义，个数可变）、表格列、状态标签色、空/加载/错误态 | **要写"变了几处"**，不用写样式 |
| **L2** | 自由层 | 字段名与业务含义、文案、列表项、图标、页面信息密度、模块顺序 | **必须写清**，这是 AI 无法猜的部分 |

**记住：L0 永不复述，L1 只说 delta，L2 说全。**

## 2. 按钮：按「角色槽位」描述，不按数量

按钮数量因项目而异，但只要都在槽位里，样式就永远不会跑偏。

| 槽位 | 数量 | 样式 | 位置 | 典型文案 |
|---|---|---|---|---|
| 取消 | 恰好 1 | 描边 `.btn-ghost` | 最左 | 取消 |
| 次操作 | 0 ~ 2 | 描边 `.btn-ghost` | 取消右侧 | 保存草稿、预览、导出 |
| **主操作** | **恰好 1** | 橙实底 `.btn-primary` | 最右 | 保存并提交、确认删除、创建 |
| 危险 | 0 ~ 1 | 红实底 `.btn-danger` | 与主操作隔开（最左或独立区域） | 批量删除 |

**硬判据：主操作永远只有 1 个。** 如果需求想要"两个主要按钮"，那不是数量问题，是需求没想清主次 —— 必须拆成一个主 + 一个次。

描述句式：

```
✅ 好：footer 三个按钮 —— 取消(左) / 保存草稿(次操作) / 保存并提交(主操作)
❌ 差：footer 放三个按钮，保存并提交、保存草稿、取消
```

差的那句会让 AI 自己决定谁在哪、谁是主色。

---

## 3. 字段：按「语义槽位」描述

| 维度 | 锁死 | 可变 |
|---|---|---|
| 字段个数 | — | 2 ~ 12 个（超过 12 考虑分步或分组） |
| 控件类型 | **枚举 → Select、日期 → DatePicker、数字 → InputNumber、长文本 → TextArea、是/否 → Switch** | 具体用哪个字段 |
| 必填标记 | `*` 号 + 主色，放标签前 | 哪些字段必填 |
| 标签位置 | 标签在输入框上方（P-01） | — |
| 栅格 | 桌面每行 2 列，≤900px 降单列 | 哪些字段跨整行（长文本、地址） |
| 校验 | 失焦即校验、红边框 + 红字提示 | 具体规则（长度、范围、正则） |

描述句式：用表格列字段比写散文快得多。

```
| 字段 | 控件 | 必填 | 备注 |
|---|---|---|---|
| 任务编号 | Input（只读） | ✓ | 自动生成 TK-日期-序号 |
| 型材规格 | Select | ✓ | 选项来自型材库 |
| 备注 | TextArea | — | 跨整行 |
```

## 4. 用户侧只需要写三行

这是整套契约的入口。**其余全部由规范兜底。**

```
基准：P-01 两列表单（容器换成弹窗，宽度 640）
改动：字段 6→5（删「优先级」）；按钮 2→3（次操作位加「保存草稿」）
例外：无（若确有例外，写「XX 改成 44px，因为触屏工位」）
```

三行 = 基准 / 差异 / 例外。这套写法能覆盖 90% 的复用需求。

如果连基准都不知道，就说业务意图，让 AI 去登记表里找：

```
场景：桌面上录入一条加工任务，字段 5 个，有 2 个必填
要求：按规范，别自创样式
```

## 5. AI 侧必须执行的流程

### 收到需求后，先填这 7 项（缺的用合理默认，但要标注）

| # | 项目 | 说明 |
|---|---|---|
| 1 | 基准变体 | P-编号；没有匹配项就先问用户，禁止自创布局 |
| 2 | 容器形态 | 卡片 / 弹窗（宽度） / 抽屉（宽度） / 独立页面 |
| 3 | 字段清单 | 名称 / 控件 / 必填 / 校验 / 是否跨整行 / 默认值 |
| 4 | 按钮清单 | 按槽位（取消 / 次操作 / 主操作 / 危险），不按数量 |
| 5 | 状态覆盖 | 空态、加载态、错误态、禁用条件、字段联动 |
| 6 | 允许偏差 | 本次明确要偏离规范的地方 + 理由；没有就写「无」 |
| 7 | 交付物 | 代码（可运行）+ 差异清单 + 验收结果 |

### 交付时，必须回一份「差异清单」

这是让下次复述更省力的关键 —— 用户下次可以直接复制这份清单当需求。

```
与 P-01 v1.1.0 的差异：
+ 容器：卡片 → 弹窗（width 640）
- 字段：删「优先级」
+ 字段：加「材质」（Select，必填）
+ 按钮：次操作位加「保存草稿」
= 其余（色彩/圆角/字号/高度/间距/footer 形态）零偏差
```

### 交付前的自检（不用用户提醒）

- 每个按钮都带 `.btn` 骨架类（否则直角黑边）
- footer 两按钮起、右对齐、取消在左、主操作在右、无分隔线
- 组件 CSS 里没有写死 `height:32px` / `font-size:14px`
- 字段控件类型符合语义映射
- 差异清单里每一行都能在代码里找到对应位置

## 6. 反例对照：这些话会导致跑偏

| 说法 | 问题 | 改成 |
|---|---|---|
| "做个好看的表单弹窗" | 没有基准，AI 自由发挥 | "按 P-01，容器换成弹窗，宽度 640" |
| "按钮加一个保存草稿" | 没说位置和角色 | "次操作位加「保存草稿」（描边，取消右侧）" |
| "颜色用橙色" | 橙色有很多种 | "主色按规范 `#EE6402`，不要调" |
| "字段跟上次差不多" | 无法核对，只能猜 | 直接列字段表 |
| "样式你看着调" | 全部失控 | 明确说"L0 不动，L2 里文案可以改" |
| "参考一下这个截图" | 截图没说明哪里参考 | "参考截图的信息分组，样式仍按规范" |

## 7. 常见需求的快速套用

**新表单弹窗（字段不同于母版）**
```
基准：P-01（卡片 → 弹窗 640）
改动：字段见下表；按钮 = 取消 + 保存并提交
例外：无
```

**列表页加一列**
```
基准：现有表格（组件规范里的表单卡片）
改动：加一列「材质」（80px，纯文本）；其余列宽不动
例外：无
```

**详情弹窗（只读，不要按钮）**
```
基准：P-02 详情描述列表
改动：容器换成弹窗 780；footer 不要（footer:null）
例外：无
```

**确实要偏离规范**
```
基准：P-01
改动：…
例外：主按钮高度 44px —— 车间触屏工位，32px 手指点不准
```
写成这样，将来别人看到会知道是刻意为之，而不是手滑。

## 8. 场景：接手已有项目，只改样式

这是最容易翻车的一类需求。项目功能已齐，只需要套外观，但 AI 有五个固定的坏习惯，必须逐条封住：

| AI 会犯的毛病 | 后果 | 用什么话封住 |
|---|---|---|
| 顺手重构 | 逻辑被改写，回归测试全废 | 「不要动」清单 + 「一行都别改」 |
| 把示例内容带进项目 | 字段、文案被污染 | 「示例只是看样式」 |
| 自创样式 | 又出现第二个视觉体系 | 「必须对齐」给具体数值，并指定 skill |
| 反复问小细节 | 十轮确认，进度归零 | 默认值条款：「别问我这些」 |
| 悄悄扩大范围 | 改了三页变十页，没法回滚 | 分阶段：先只改 1 个页面 |

### 8.1 指令模板（直接复制，改第 1、5、6 行）

```
【任务性质】只改样式，不重写功能。这个项目功能已齐，只套我方视觉规范。

【不要动】业务逻辑、数据结构、组件拆分、路由、接口调用、状态管理 —— 一行都别改。
         如果某个样式必须动结构才能生效，先说明要动哪、为什么，等我确认再做。

【内容以我方为准】字段、文案、数据按我给的清单来。项目里原有内容不要改写、
                不要"优化措辞"、不要自己补字段。我给的参考示例只看样式，
                示例里的字段和示例数据不要带进项目。

【必须对齐】按 dajie-orange-design-spec：主色 #EE6402、四级文字色阶（85/65/45/25% 黑）、
          字号 16/14/12、圆角 12/4/2、控件高 32、间距 8 网格、按钮三档 40/32/24、
          弹窗底部两按钮右对齐且取消在左、全站零默认蓝。

【参考即可】表单几列、区块顺序、用卡片还是弹窗、筛选区位置 —— 按现有功能的信息量定，
          不用强行套我的示例，也不用为此来问。

【别问我这些】清单之外的细节，按规范的默认值执行，自行决定，最后列出来就行。

【做完给我】1) 改了哪些文件、每个文件具体改了什么
          2) 与规范的例外项及原因
          3) 自检：有没有直角黑边按钮（缺 .btn 骨架类）、有没有默认蓝残留、
             有没有写死 height:32px / font-size:14px 这类硬编码
```

### 8.2 分阶段，别一次全量

```
第一步：只挑 1 个最有代表性的页面改完给我看，确认后再推其余页面。
```

这条对 AI 和人一样有效。AI 一次改十个文件，出问题你只能整体回滚；先改一个，30 分钟就能校准它的理解，而且这一步能暴露出它对规范的实际掌握程度。

### 8.3 让它自己交「改动清单」

不要接受「已经全部改好了」这种结论式回答。要求它列出文件级改动 + 例外项，你才能核对它有没有越界。清单格式：

```
改动文件（3）
- 加工列表.html：样式块新增 12 条规则；未动渲染逻辑
- data.js：未改动
例外（1）
- 表格行高 36px（原 40px）—— 列数多，40px 一屏放不下
自检：无直角黑边按钮 / 无默认蓝 / 硬编码 0 处
```

最后一行「未改动」也要它写出来。写"未改动"的成本很低，但它会逼 AI 真的去看一遍。

### 8.4 一句话版本

临时用、懒得写全的时候，至少说这三句：

> 1. 只改样式，别动逻辑和数据结构。
> 2. 内容按我给的来，参考示例只看样式别抄内容。
> 3. 样式全按 dajie-orange-design-spec，别自创；细节自己定，最后列改动清单。
